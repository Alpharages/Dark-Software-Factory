Independent verification pass. Both servers started (backend `:3000` on the **live DB**, frontend `:5173`), and **one real ticket was run end-to-end through the actual product flow** (UI "Sync from ClickUp" → dispatcher → execution → record), _not_ the `/executions/test` shortcut.

**Setup:** status→skill map narrowed to a single `to do → clickup-dev-implement`; exactly **one** ClickUp ticket (Story 11.1 "AI consent and opt-in flow", `86exz3qzx`) moved to `to do`; claude session file-bridged; account usage reset (it was at **4,772,868** tokens vs a 1,000,000 weekly budget — EXEC-CRIT-4 still unfixed). Sync clicked in the UI → only that ticket dispatched (all others logged `Dispatch skipped: no skill mapping`) → execution **`1b1c1db7`** on **claude/sonnet**.

**What the AI did (ground truth from the worktree):** wrote **7 files** — `components/ui/AiConsentCard.tsx`, `hooks/use-ai-consent.ts`, `app/settings.tsx`, `components/ui/index.ts`, plus 3 test files. Execution finished **COMPLETED** with the summary _"Implemented CU-86exz3qzx (Story 11.1: AI consent and opt-in flow) end-to-end"_.

**What DSF recorded:**

| Check                  | Result                                                 |
| ---------------------- | ------------------------------------------------------ |
| `files_changed`        | **`[]` (0)** — identical to the original bug           |
| Branch `ohp/86exz3qzx` | **no agent commit** — HEAD still at base `69fe144`     |
| Worktree               | **torn down** → the 7 files **permanently destroyed**  |
| Execution status       | **COMPLETED**, summary claims "implemented end-to-end" |

**Root cause of the fix's failure.** `resolveChangedFiles` only reads the **committed** diff:

```ts
execFileSync('git', ['-C', workspaceDir, 'diff', '--name-only', `${base}...HEAD`]); // three-dot = commits only
```

This run the agent **never committed**, so `HEAD == base` → the diff is empty → it falls back to `parserFiles`, which is **always empty on the claude runtime** (the code's own comment says the claude runtime never emits `files_changed` events) → `files_changed = []`. The earlier run (`ohp/86exz3t04`) only produced 8 files because that agent _happened_ to commit. **The fix depends on non-deterministic agent behaviour.** Its 5 unit tests pass because they mock an already-committed diff.

**Severity is now higher than the original bug:** the platform reports **COMPLETED / "implemented end-to-end"** while (a) the approval gate stays blind (`files_changed=0`, Approve & Push disabled), and (b) the agent's actual work is **deleted** on teardown. That is silent data loss dressed as success.

**Correct fix (recommended):**

1. Don't trust the agent to commit. Before teardown, capture the **working tree**: `git add -A` → `git diff --cached --name-only` (or `git status --porcelain` + `git ls-files --others --exclude-standard`).
2. Better: have the **runner** commit the agent's work deterministically onto `ohp/<taskId>`, then read the diff — so the branch is always the durable artifact.
3. Fail loudly: if the agent's summary claims implementation but **zero** changes are captured, the execution must **not** be `COMPLETED` — mark it failed/needs-attention rather than silently discarding the work.

**Also re-confirmed live this pass:** ✅ SYNC-1 genuinely fixed (log now reads `Processing message for task 86exz3qzx`, previously `task undefined`); ✅ prefetch=1 held (only one execution dispatched from a 93-task sync).

## §2.1e — EXEC-CRIT-5 RE-FIXED AND VERIFIED LIVE (2026-07-16, second pass)

Re-tested through the **real product flow** (UI "Sync from ClickUp" → dispatcher → execution), on the **same ticket that failed in §2.1d** (`86exz3qzx`), with the branch baselined at `69fe144` (no agent commit) beforehand.

**The fix (three parts):**

1. **Capture the working tree, not just commits.** `resolveChangedFiles` now returns the committed diff (`base...HEAD`) **∪** `git status --porcelain=v1 -z --untracked-files=all`. The claude runtime emits no `files_changed` events and the agent often never commits, so the committed diff alone captured nothing.
2. **Don't trust the agent to commit.** `commitPendingWork` sweeps the worktree onto `ohp/<taskId>` after the formatter and **before** teardown, authored `Dark Software Factory <bot@dsf.local>` (inline identity — no dependence on ambient git config). The branch is the durable artifact the diff, the approval gate and the push all read.
3. **Fail loudly.** An implement run that captures **zero** files is now marked **FAILED** with the agent's summary attached, instead of reporting COMPLETED / "implemented end-to-end".

**Live result — execution `a46d77ab` (claude/sonnet, 1185s):** the agent again wrote its work and **never committed** (the exact §2.1d condition, reproduced).

| Check                        | §2.1d (before)                | Now                                          |
| ---------------------------- | ----------------------------- | -------------------------------------------- |
| `files_changed`              | `[]` (0)                      | **7 files**                                  |

**A bug the live test caught that unit tests did not.** The first re-fix attempt guarded the sweep with `git add -A -- . ':(exclude)node_modules'` (to keep the runner's `node_modules` symlink out of the branch). The throwaway verification repo had no `.gitignore`, so it passed while the live run failed — **the same class of false-green that let the original fix ship.** Fixed by excluding `node_modules` via git's own `info/exclude` at worktree provision, making the sweep a plain `git add -A`; verified against real git in **both** repo shapes (with and without `.gitignore`).

### EXEC-CRIT-4 — token over-counting: root cause found, 50.6× error eliminated

**Not quota sizing, and not double-counting.** The parser added `cache_read_input_tokens` to input at **1:1** (`openharness-stream.parser.ts:184`). Claude's terminal `result.usage` reports that field **cumulatively across every turn**, and on an agentic run the cached prefix is the entire conversation — so it grows ~O(turns × context) and dwarfs the actual work. A cache read is a re-read of an already-processed prefix, not new work.

Fix: cache reads are now reported separately (`cachedInputTokens`) and **excluded** from budget metering. `cache_creation_input_tokens` stays counted — that genuinely is fresh input the model processed. The runner logs the split so the accounting is auditable without a schema change.

**Live proof — execution `129d1d77`, real UI Sync flow → dispatcher → execution, claude/sonnet, COMPLETED in 790s, 7 files:**

### §3.5 — configurable execution concurrency: BUILT (global + per-project)

- **Global** — `SystemConfig` key `execution.concurrency_limit` (env fallback `EXECUTION_CONCURRENCY_LIMIT`, default **1**) drives `channel.prefetch(n)`. Prefetch already gives the exact requested "run at most N, hold the rest in the queue" semantics, since the base consumer acks only after the full run. Applied at consumer start → a change takes effect on backend restart. UI: **Settings → System Configuration → "Max Concurrent Executions"**.
- **Per-project** — nullable `Project.execution_concurrency_limit` (null = inherit global), mirroring the existing `require_pr_approval` pattern. Enforced by the new `ExecutionConcurrencyGate` in the dispatcher, because prefetch is per-_consumer_ and carries no project context. UI: **Project Settings → General**; blank = inherit, minimum 1. Migration `20260720145353_add_execution_concurrency_limit`.

The report's §3.5 note suggested nack-with-requeue for the per-project cap. That was **not** used: there is no requeue path in the consumer base (both branches dead-letter), and immediate requeue hot-spins on a single-consumer queue. Instead the gate waits for a slot in-process and releases in a `finally`. Waiters are bounded by the global prefetch, so the queue cannot grow unbounded. In-process only, matching the existing `inFlightTickets` guard — documented as needing a shared counter for multi-instance.

| ---------------------------------- | ---------------------------------------------------------- |
| Global config `3` → queue          | **`ticket-intake-queue prefetch = 3`**                     |
| Global config `1` → queue          | **`prefetch = 1`**                                         |
| 66-task sync under `prefetch=1`    | **`ready=0, unacked=1`** — exactly one execution in flight |
| `PATCH /projects/:id` limit `2`    | stored **2**                                               |
| `PATCH /projects/:id` limit `0`    | rejected **400**                                           |
| `PATCH /projects/:id` limit `null` | reset to inherit (NULL in DB)                              |

> **A race the unit tests caught before it shipped.** The first cut of the gate read the active count _before_ awaiting the limit lookup. A release landing in that window left the caller queued behind a wake-up that had already fired — a permanent hang. The count is now read only _after_ the await, in the same synchronous step that registers the waiter.

## 3.5 CRITICAL FEATURE GAP — execution concurrency limit must be configurable (global + per-project)

> `[✅ BUILT + VERIFIED LIVE 2026-07-20 — see §2.1f.` Global = `SystemConfig` key **`execution.concurrency_limit`** (env fallback `EXECUTION_CONCURRENCY_LIMIT`, default 1) driving `channel.prefetch(n)`; per-project = nullable **`Project.execution_concurrency_limit`** enforced by `ExecutionConcurrencyGate` in the dispatcher. Both UI-editable. Note the key/column names differ from the names proposed below, and the per-project cap does **not** use nack-with-requeue as suggested in "Implementation notes" — see §2.1f for why.`]`

**The problem (Sir's requirement).** When "Sync from ClickUp" is clicked, every AI-actionable ticket is queued for execution. There must be a way to say _"run at most N executions at a time; hold the rest in a queue until slots free up,"_ and that N must be **settable from the UI — a global default AND a per-project override** (mirroring the existing status→skill map pattern, which already has a `SystemConfig` global + per-project override).

**Current behaviour (verified in code).** The mechanism _partly_ exists but is **hardcoded and not configurable**:

- `syncFromClickUp()` (`src/projects/project.service.ts:579`) publishes each task to the **RabbitMQ `ticket-intake` queue** — good, it's a real queue, not a parallel blast.
- The intake consumer sets **`channel.prefetch(5)`** (`src/ticket-intake/ticket-intake.consumer.ts:55`), and the base consumer **acks only after the full run** (`src/rabbitmq/rabbitmq-consumer.base.ts:29→32`; `dispatch()` awaits the entire execution). So today the effective cap is **exactly 5 concurrent executions, rest wait in the queue.**
- **There is NO setting for this** — no env var, no `SystemConfig` key, no UI, no per-project field. The `5` is a magic number in code. (Full config/env scan confirms nothing like `MAX_CONCURRENT_EXECUTIONS`/`AI_EXECUTION_CONCURRENCY` exists.)

**Required feature.**

1. **Global default** — a configurable "max concurrent executions" (default **1**). Surface it in **Settings → System Configuration** (same UI area as Cleanup/Self-Healing/etc.), backed by a `SystemConfig` key (e.g. `execution.concurrency.global`), env fallback `AI_EXECUTION_CONCURRENCY`.
2. **Per-project override** — an optional "max concurrent executions" on each project, editable in **Project Settings** (`/projects/:id/settings`) and/or the Projects & Sync row. Effective limit = `project.maxConcurrentExecutions ?? global`. Store as a column on `projects` (or in the existing per-project **sync-config** that already exists — `GET/PATCH /projects/:id/integration/sync-config` — a natural home).

**Implementation notes (important nuance).**

- **Global** is easy: drive `channel.prefetch(n)` from config instead of the literal `5`. `prefetch(1)` = one-at-a-time, rest queue in RabbitMQ automatically (the wait-queue behaviour Sir wants already comes free from RabbitMQ).
- **Per-project is NOT achievable with prefetch alone** — RabbitMQ prefetch is per-_consumer_ (global), not per-project.
