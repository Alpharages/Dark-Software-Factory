## 3.5 CRITICAL FEATURE GAP — execution concurrency limit must be configurable (global + per-project)

**The problem (Sir's requirement).** When "Sync from ClickUp" is clicked, every AI-actionable ticket is queued for execution. There must be a way to say _"run at most N executions at a time; hold the rest in a queue until slots free up,"_ and that N must be **settable from the UI — a global default AND a per-project override** (mirroring the existing status→skill map pattern, which already has a `SystemConfig` global + per-project override).

**Current behaviour (verified in code).** The mechanism _partly_ exists but is **hardcoded and not configurable**:

- `syncFromClickUp()` (`src/projects/project.service.ts:579`) publishes each task to the **RabbitMQ `ticket-intake` queue** — good, it's a real queue, not a parallel blast.
- The intake consumer sets **`channel.prefetch(5)`** (`src/ticket-intake/ticket-intake.consumer.ts:55`), and the base consumer **acks only after the full run** (`src/rabbitmq/rabbitmq-consumer.base.ts:29→32`; `dispatch()` awaits the entire execution). So today the effective cap is **exactly 5 concurrent executions, rest wait in the queue.**
- **There is NO setting for this** — no env var, no `SystemConfig` key, no UI, no per-project field. The `5` is a magic number in code. (Full config/env scan confirms nothing like `MAX_CONCURRENT_EXECUTIONS`/`AI_EXECUTION_CONCURRENCY` exists.)

**Required feature.**

1. **Global default** — a configurable "max concurrent executions" (default **1**). Surface it in **Settings → System Configuration** (same UI area as Cleanup/Self-Healing/etc.), backed by a `SystemConfig` key (e.g. `execution.concurrency.global`), env fallback `AI_EXECUTION_CONCURRENCY`.
2. **Per-project override** — an optional "max concurrent executions" on each project, editable in **Project Settings** (`/projects/:id/settings`) and/or the Projects & Sync row. Effective limit = `project.maxConcurrentExecutions ?? global`. Store as a column on `projects` (or in the existing per-project **sync-config** that already exists — `GET/PATCH /projects/:id/integration/sync-config` — a natural home).

**Implementation notes (important nuance).**

- **Global** is easy: drive `channel.prefetch(n)` from config instead of the literal `5`. `prefetch(1)` = one-at-a-time, rest queue in RabbitMQ automatically (the wait-queue behaviour Sir wants already comes free from RabbitMQ).
- **Per-project is NOT achievable with prefetch alone** — RabbitMQ prefetch is per-_consumer_ (global), not per-project. A per-project cap needs **app-level accounting** before running: in the dispatcher, before `runForTicket`, count this project's active executions (`status IN (QUEUED, IN_PROGRESS)` — the existing `checkActiveExecution` query already does this shape, just make it count-per-project) and if `>= projectLimit`, **requeue the message** (nack-with-requeue or a short delayed re-publish) so it waits without spinning. This reuses infrastructure already present.
- Keep the existing per-ticket dedup (`inFlightTickets` + `checkActiveExecution`) — that stays; this adds a _count_ cap on top of the _dedup_.

**Priority:** high. Combined with EXEC-CRIT-4 (one claude run = 1.18M tokens = whole weekly budget), an uncapped/hardcoded-5 concurrency means a single sync can burn budget fast. A per-project limit of 1 during rollout is the safe default.
