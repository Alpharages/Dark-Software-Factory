# Story 4.3: Git Commit Generation & Push

**Status:** drafted

## Story

As the system,
I want to commit AI-generated code and push to GitHub,
So that code changes are versioned and traceable.

## Acceptance Criteria

### AC#1: AI-Generated Code Collection

**Given** a feature branch has been created (Story 4.2)
**When** the system prepares to commit code
**Then** it:

- Loads execution.code_output from database (stored as JSON/JSONB)
- Parses files_changed array to extract all modified files
- Creates file tree structure with proper paths
- Handles file types: create, modify, delete operations
- Validates all file paths are within repository bounds (security: no path traversal)
- Supports binary and text files
- Encoding: UTF-8 for text files, base64 for binary files

**Example execution.code_output structure:**

```json
{
  "files_changed": [
    {
      "path": "src/users/user.service.ts",
      "operation": "modify",
      "content": "... code content ...",
      "encoding": "utf-8"
    },
    {
      "path": "src/users/dto/create-user.dto.ts",
      "operation": "create",
      "content": "... code content ...",
      "encoding": "utf-8"
    }
  ]
}
```

### AC#2: Conventional Commit Message Generation

**Given** code files are collected
**When** the system generates a commit message
**Then** it follows conventional commits specification:

**Format:**

```
{type}({scope}): {short description}

{longer description from ticket}

Implements: {ticket_id}
AI-Generated: {ai_provider}
Execution-ID: {execution_id}
Complexity: {complexity_score}/100
```

**Type determination:**

- `feat`: New features (analyze ticket description for keywords: "add", "implement", "create")
- `fix`: Bug fixes (keywords: "fix", "resolve", "bug")
- `refactor`: Code refactoring (keywords: "refactor", "restructure", "optimize")
- `test`: Test additions/changes (keywords: "test", "testing")
- `docs`: Documentation (keywords: "document", "readme")
- `chore`: Maintenance tasks (keywords: "update", "upgrade", "dependency")

**Scope extraction:**

- Parse files_changed paths to determine affected module
- Examples: `auth`, `users`, `tickets`, `qa`, `github`
- Use first directory in path: `src/auth/` → scope: `auth`
- Multiple modules: Use primary module or `multiple`

**Short description:**

- Maximum 72 characters
- Lowercase, imperative mood: "add user authentication" (not "adds" or "added")
- Extract from ticket title, sanitized

**Longer description:**

- Include ticket description summary (first 3-5 sentences)
- List key files changed (max 10 files)
- Generated by AI provider context

**Metadata:**

- Implements: ticket.clickup_task_id (e.g., "DSF-123")
- AI-Generated: execution.ai_provider (CURSOR_HEADLESS or CLAUDE_CODE)
- Execution-ID: execution.id (UUID for traceability)
- Complexity: execution.complexity_score (from Story 2.3)

### AC#3: Git Tree and Commit Creation

**Given** files and commit message are prepared
**When** the system creates the commit
**Then** it uses GitHub API in this order:

1. **Get base tree SHA:**
   - GET `/repos/{owner}/{repo}/git/refs/heads/{branch_name}`
   - Extract commit SHA from response
   - GET `/repos/{owner}/{repo}/git/commits/{commit_sha}`
   - Extract tree SHA from commit

2. **Create blobs for each file:**
   - POST `/repos/{owner}/{repo}/git/blobs` for each file
   - Request body: `{ content: base64_encoded_content, encoding: "base64" }`
   - Store returned blob SHA for each file

3. **Create tree:**
   - POST `/repos/{owner}/{repo}/git/trees`
   - Include base_tree SHA (from step 1)
   - Tree entries: `{ path, mode, type: "blob", sha: blob_sha }`
   - File modes: `100644` (regular file), `100755` (executable), `040000` (directory)
   - Store returned tree SHA

4. **Create commit:**
   - POST `/repos/{owner}/{repo}/git/commits`
   - Body: `{ message, tree, parents: [parent_commit_sha], author: {name, email, date}, committer }`
   - Author: Configured bot identity (from env: `GITHUB_BOT_NAME`, `GITHUB_BOT_EMAIL`)
   - Store returned commit SHA

5. **Update branch reference:**
   - PATCH `/repos/{owner}/{repo}/git/refs/heads/{branch_name}`
   - Body: `{ sha: new_commit_sha, force: false }`
   - Verify response status: 200 OK

### AC#4: Database Record Updates

**Given** commit is successfully pushed
**When** the operation completes
**Then** the system:

- Updates `github_pushes` record (created in Story 4.2):
  - commit_sha: new commit SHA from GitHub
  - push_status: BRANCH_CREATED → PUSHED
  - updated_at: current timestamp
- Creates audit log entry via AuditLogService:
  - operation: "github_commit_push"
  - entity_type: "execution"
  - entity_id: execution.id
  - details: { repository, branch_name, commit_sha, files_count, ai_provider }
  - user_id: "system" (automated operation)
  - created_at: timestamp
- Updates execution status (optional): execution.status remains IN_PROGRESS (Story 4.4 will complete)

### AC#5: Error Handling & Resilience

**Given** commit/push operations may fail
**When** errors occur
**Then** the system handles them appropriately:

**Authentication Errors (401/403):**

- Log to SentryService with full context
- Update github_pushes.push_status = AUTH_FAILED
- Update github_pushes.error_message with sanitized error
- Update execution.status = FAILED
- Post comment to ClickUp ticket: "GitHub authentication failed. Please check credentials."
- Do NOT retry (non-retryable)

**Rate Limit Errors (429):**

- Use RetryHandlerService.scheduleRetry() from Story 2.9
- Publish to `github-retry-queue` with delay from X-RateLimit-Reset header
- Message payload: `{ executionId, operation: 'commit_push', repository, branchName, retryCount, context }`
- Max 3 retry attempts: delays 1min, 5min, 15min
- Track metric: `github_rate_limit_hit_total{operation="commit_push"}`

**Conflict Errors (422 Unprocessable Entity):**

- Possible cause: Branch was updated by another process
- Resolution: Fetch latest branch SHA, rebase changes, retry commit creation
- Max 2 retry attempts
- Log warning: "Commit conflict detected, retrying with latest branch state"

**Network/Transient Errors (5xx, timeout):**

- Use RetryHandlerService with exponential backoff
- Retry attempts: 3 times with delays 2s, 4s, 8s
- Include retry count in Sentry context
- After max retries: Mark as failed, notify PM

**File Size Limits:**

- GitHub blob size limit: 100 MB per file
- Validate each file before creating blob
- If file exceeds limit: Skip file, log error, add to error_message
- Continue with other files if possible

### AC#6: Observability & Metrics

**Given** commit/push operations execute
**When** metrics are recorded
**Then** the system tracks:

**Prometheus Metrics:**

- `github_commits_created_total{status, repository, ai_provider, scope}` - Counter
- `github_commit_duration_seconds{repository, operation}` - Histogram
  - Operations: create_blobs, create_tree, create_commit, update_ref
- `github_push_success_total{repository, branch_type}` - Counter (branch_type: feature, hotfix)
- `github_files_pushed_total{repository, file_type}` - Counter (file_type: typescript, javascript, json, etc.)
- `github_commit_size_bytes{repository}` - Histogram (total size of all files in commit)

**Structured Logging:**

- All operations logged via LoggerService with:
  - executionId, ticketId, repository, branch_name, commit_sha
  - files_count, total_size_bytes, ai_provider, complexity_score
  - duration_ms for each GitHub API call
  - correlationId (from execution context)

**Audit Trail:**

- Every commit logged to audit_logs table
- Includes: who (system), what (commit_push), when (timestamp), where (repository), why (ticket reference)

## Dev Notes

### Architecture Context

**Epic Goal:** Epic 4 completes the automated pipeline from ticket to production. Story 4.3 commits AI-generated code to feature branches, enabling version control, traceability, and code review.

**Workflow Position:**

```
Ticket → AI Generation → QA Checks (Epic 3) → Branch Creation (4.2) → ✅ Commit & Push (This Story) → PR Creation (4.4) → CI/CD (4.5-4.6)
```

**Design Philosophy:**

- **Conventional Commits:** Industry standard for automated changelogs, semantic versioning
- **Git API vs Git CLI:** Using GitHub API provides better error handling, no local git setup required, works in containerized environments
- **Atomic Operations:** Each commit represents one logical unit (one ticket execution)
- **Traceability:** Every commit links back to ticket, execution, AI provider for full audit trail

### Technical Requirements

**GitHub API Workflow:**

The Git Data API requires this specific sequence (cannot be reordered):

1. **Get base tree:** Latest commit's tree SHA (starting point for changes)
2. **Create blobs:** Each file becomes a blob object (content-addressed storage)
3. **Create tree:** Combines blobs into directory structure
4. **Create commit:** Points to tree + parent commit(s)
5. **Update ref:** Moves branch pointer to new commit

Why this order? Git's immutable object model: blobs → trees → commits → refs.

**Conventional Commits Specification:**

- Format: `<type>(<scope>): <subject>` (first line)
- Types: feat, fix, docs, style, refactor, perf, test, build, ci, chore, revert
- Scope: Module/component affected (e.g., auth, users, api)
- Subject: Imperative mood, lowercase, no period, max 72 chars
- Body: Optional longer description (wrap at 72 chars)
- Footer: Breaking changes, issue references

See: https://www.conventionalcommits.org/en/v1.0.0/

### Security Considerations

**File Path Validation (CRITICAL):**

```typescript
// Prevent path traversal attacks
function validateFilePath(path: string): boolean {
  // Reject paths with directory traversal patterns
  if (path.includes('..') || path.includes('~')) {
    return false;
  }

  // Must be relative path within repository
  if (path.startsWith('/') || path.includes(':')) {
    return false;
  }

  // Validate against allowed directories
  const allowedPrefixes = ['src/', 'test/', 'docs/', 'scripts/', 'config/'];
  return allowedPrefixes.some((prefix) => path.startsWith(prefix));
}
```

**Token Security:**

- GitHub tokens automatically redacted by LoggerService (Story 1.7)
- Never log commit content (may contain secrets)
- Sanitize error messages before storing in database
- All GitHub operations use GitHubService with secure auth

**Content Validation:**

- Scan commit content for secrets before pushing (use existing SecretsScanner from Story 3.4)
- Reject commits containing: API keys, passwords, tokens, private keys
- Log rejected commits to Sentry with sanitized details
- Notify PM if secrets detected: "Commit blocked - potential secrets detected"

**Audit Trail:**

- Every commit push logged to audit_logs table
- Include: executionId, repository, branch_name, commit_sha, files_count
- Capture: timestamp, ai_provider, complexity_score
- Enable forensics: "Who pushed what, when, and why?"
