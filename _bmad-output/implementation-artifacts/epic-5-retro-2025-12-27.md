## 3. Challenges & Critical Discoveries

### 🔴 1. Performance Trap: N+1 Queries in Dashboards
**Charlie:** "Story 5.4 (Workload) initially had a massive N+1 query problem. Calculating utilization for 20 PMs triggered 20 separate DB calls plus sub-queries for tickets."
**Fix:** Refactored to use Prisma `groupBy` and `aggregate` in a single query.
**Lesson:** Dashboard widgets MUST use aggregation queries. No loops over entities.

### 🔴 2. The "Stub" Trap
**Elena:** "I stubbed the ClickUp integration in Story 5.5 because it felt 'too big' for the story. But I didn't create the follow-up story immediately, which caused a momentary blocker."
**Fix:** Created Story 5.5.1 immediately upon realization.
**Lesson:** If you stub a core requirement, the follow-up story must be created *instantly* and linked as a blocker.

### 🔴 3. Frontend Delegation Complexity
**Bob (SM):** "We delegated the entire `dsf-dashboard` repo to AI. While fast, the UX required significant manual polish (Story 5.7) for keyboard shortcuts and accessibility."
**Lesson:** AI builds the *structure* of UI fast, but *usability* (shortcuts, smooth states) still needs specific "UX Polish" stories.

## 4. Key Insights & Lessons Learned

### 💡 The "Integration Sub-Story" Pattern
When a story requires a complex 3rd-party integration (like ClickUp or Slack), do not jam it into the main feature story.
**Pattern:**
1. **Feature Story:** "User can click a button to sync" (Interface + Stub)
2. **Integration Story:** "Implement the actual API connector" (Backend plumbing)
This separation allows parallel development and cleaner testing.

### 💡 Pre-emptive Aggregation for Analytics
Any story with the word "Dashboard" or "Report" in the title must list "Query Performance / N+1 Prevention" in its Non-Functional Requirements (NFRs). Reviewers should reject code using loops for data fetching.
