## 2. What Went Well

- **Atomic Locking:** The partial unique index strategy in Postgres (`UNIQUE (file_path) WHERE status = 'LOCKED'`) provided rock-solid concurrency control.
- **E2E Validation:** The comprehensive `dependency-flow.e2e-spec.ts` successfully simulated complex multi-ticket dependency chains.
- **Architectural Isolation:** Dependency logic was encapsulated in its own module (`DependenciesModule`), making integration into the main pipeline (12.5) clean and non-disruptive.
- **AI Reasoning:** Using `AIDecisionLoggerService` allowed us to trace _why_ specific branches were selected, boosting team confidence in the v3 logic.

---

## 3. Challenges & Lessons Learned

- **Latency vs. Safety:** File prediction adds ~15-20s to the intake Flow. While safe, it impacts the perceived "speed" of the system.
- **Queue Throttling:** Rapid-fire dependency resolutions can cause temporary ETA staleness in the UI before re-calculation completes.
- **Prisma Limitations:** Handling partial indexes required manual SQL migrations, which can be easily overlooked in purely Prisma-driven environments.
- **Cost Growth:** The addition of 3-4 new AI calls per ticket (Prediction, Reasoning, Strategy) increases token consumption.

---

## 4. Key Insights & Patterns Discovered

### 💡 Pattern: Atomic Gatekeeping

We've established a "Gatekeeper" pattern where tickets must pass through three distinct validations (Cycle Check → Blocker Check → File Lock) before being granted an `Execution` context.

### 💡 Pattern: Deterministic Fallbacks

For the Branch Strategist, we combined deterministic rules (0 or 1 dependency) with AI reasoning for complex cases, ensuring speed for simple tickets and intelligence for complex ones.
