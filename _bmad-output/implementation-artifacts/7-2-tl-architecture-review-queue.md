# Story 7.2: TL Architecture Review Queue

Status: done

## Story

As a TL,
I want a dedicated queue of architecture decisions requiring my review,
So that I can efficiently approve/reject AI's technical choices.

## Acceptance Criteria

1. **Given** ADRs are generated by AI
   **When** I access my TL review queue
   **Then** I see:
   - List of pending ADRs (status: Proposed)
   - Priority indicators (high-risk vs. low-risk decisions)
   - Ticket context (what feature is this for)
   - AI confidence level for each decision

2. **And** I can filter/sort by:
   - Risk level (high-risk decisions first)
   - Project
   - Date created
   - AI confidence (review low-confidence first)

3. **And** each ADR shows:
   - Quick preview of decision
   - "Review" button (<3 clicks per NFR-UX2)
   - Time estimated for review (based on complexity)

### Database Schema (Story 7.1)

```prisma
model Adr {
  id                String   @id @default(uuid())
  title             String
  status            AdrStatus @default(PROPOSED)
  context           String   @db.Text
  decision          String   @db.Text
  consequences      String   @db.Text
  alternatives      String   @db.Text
  confidence        Float    // 0.0-1.0
  risk_level        RiskLevel?
  execution_id      String?
  execution         Execution? @relation(fields: [execution_id], references: [id])
  ticket_id         String?
  ticket            Ticket?    @relation(fields: [ticket_id], references: [id])
  created_at        DateTime @default(now())
  updated_at        DateTime @updatedAt
}

enum AdrStatus {
  PROPOSED
  APPROVED
  REJECTED
  MODIFIED
  DEFERRED
}

enum RiskLevel {
  LOW
  MEDIUM
  HIGH
}
```

**Example Query Implementation:**
```typescript
// getReviewQueue() Prisma query with nested ticket relations
const adrs = await this.prisma.adr.findMany({
  where: {
    status: filters.status || AdrStatus.PROPOSED,
    risk_level: filters.risk_level,
    ticket: filters.project_id ? {
      project_id: filters.project_id
    } : undefined,
    confidence: {
      gte: filters.min_confidence,
      lte: filters.max_confidence
    }
  },
  include: {
    execution: {
      include: {
        ticket: {
          select: {
            id: true,
            title: true,
            clickup_id: true,
            project_id: true
          }
        }
      }
    }
  },
  orderBy: {
    [filters.sort_by || 'risk_level']: filters.sort_order || 'desc'
  }
});
```

### API Specification

**Endpoint:** `GET /api/v1/architecture-review/queue`

**Query Parameters:**
- `status` (optional): `PROPOSED` | `APPROVED` | `REJECTED` | `MODIFIED` | `DEFERRED` (default: `PROPOSED`)
- `risk_level` (optional): `LOW` | `MEDIUM` | `HIGH`
- `project_id` (optional): UUID
- `min_confidence` (optional): Float 0.0-1.0
- `max_confidence` (optional): Float 0.0-1.0
- `sort_by` (optional): `risk_level` | `created_at` | `confidence` (default: `risk_level`)
- `sort_order` (optional): `ASC` | `DESC` (default: `DESC`)

**Response:** `200 OK`

### Known Risks & Considerations

1. **Risk Level Backfill:** If existing ADRs have `risk_level: null`, need migration or service method to calculate it
   - **Mitigation:** Check in `getReviewQueue()` and apply default calculation on-the-fly if null

2. **Ticket Relations:** ADR → Execution → Ticket (two-hop relation)
   - **Mitigation:** Use Prisma `include: { execution: { include: { ticket: true } } }` to fetch in single query

3. **Empty Queue:** If no ADRs with status `PROPOSED`, endpoint returns empty array
   - **Mitigation:** This is expected behavior, just return `{ items: [], total: 0 }`

4. **Performance:** No pagination implemented (Epic 7.2 scope is MVP)
   - **Mitigation:** Acceptable for Phase 1 (assumed <100 pending ADRs). Add pagination in future story if needed.

5. **Error Handling Patterns:**
   - Invalid `project_id` filter: Return empty array (don't throw 404)
   - Null ticket relations: Return ADR with `ticket: null` in response DTO
   - Prisma query failures: Catch and return 500 with Sentry logging
   - Invalid enum values in query params: Handled by `class-validator` (400 Bad Request)

#### Key Implementation Decisions:

1. **Response DTOs as Interfaces (Not Classes):**
   - Converted `TicketContextDto`, `AdrQueueItemDto`, `AdrReviewQueueResponseDto` from classes to interfaces
   - **Reason:** These are response-only DTOs with no validation decorators. Classes require definite assignment which causes TypeScript errors. Interfaces are cleaner for simple type definitions.
   - **Impact:** No functionality change, cleaner code, no lint errors

2. **Ticket Field Name:**
   - Used `clickup_task_id` (not `clickup_id`) to match actual Prisma schema
   - **Lesson:** Always verify field names in schema before implementing DTOs

3. **Prometheus Metrics:**
   - `adr_queue_accessed_total` counter tracks TL queue access with labels `role` and `has_filters`
   - `adr_queue_depth` gauge shows real-time count of PROPOSED ADRs
   - Uses generic `MetricsService.incrementCounter()` and `setGauge()` methods

4. **RBAC Pattern:**
   - Applied triple-guard pattern: `JwtAuthGuard` + `RolesGuard` + `ThrottlerGuard`
   - Restricted to TL and ADMIN roles only
   - Rate limiting uses default throttler config (100 req/min)

5. **Review Time Calculation:**
   - Simple switch-case based on risk level
   - Returns default 3 minutes for null risk_level
   - No database storage - calculated on-the-fly in response
